# ZhuYe Serve Wire Protocol (v0 + SDK Extensions)

<p align="center">  <a href="PROTOCOL.md">中文</a> · <b>English</b>  </p>

`zhuye serve` is a persistent stdio JSONL session server: one process
= one resident AgentThread, with multiple turns of conversation sharing
in-memory state. Both the Python and TypeScript SDKs are built on top of
this protocol — this document is the shared implementation basis of the
two SDKs, and can also be used for hand-written integrations in any
language.

- **stdin**: one `Submission` JSON object per line (UTF-8,
  `\n`-delimited).
- **stdout**: one `Event` JSON object per line.
- **stderr**: tracing logs (human-readable, not protocol data; SDKs
  pass them through or discard them).

All enum discriminators are serde `snake_case` strings (protocol v0 is
frozen: new variants are non-breaking, and clients must tolerate
unknown `"type"` values).

---

## 0. Protocol Surfaces and Versioning Policy

### 0.1 Three protocol surfaces

| Surface | Carrier | Defined in |
|---------|---------|------------|
| Submission (Op) | the mpsc channel from client → AgentThread; on `zhuye serve`, one JSON per stdin line | `crates/protocol/zhuye-protocol/src/op.rs` |
| Event (EventMsg) | AgentThread → client; on serve, one JSON per stdout line | `crates/protocol/zhuye-protocol/src/event_msg/` |
| RolloutRecord | persisted JSONL (`~/.zhuye/sessions/YYYY/MM/DD/<thread>.jsonl`) | `crates/protocol/zhuye-protocol/src/recorder.rs` |

All three share the `ThreadId` / `TurnId` newtypes and the basic
types `ContentBlock` / `ToolError` (`item.rs`).

### 0.2 Versioning policy

- Discriminators are serde `snake_case`; tolerating unknown variants
  is a **client obligation**;
- Semantic commitment: Op / EventMsg are append-only, never changed;
  if a field needs to evolve, add a new variant rather than reusing an
  old name;
- Changing the fields of an existing variant is breaking and
  forbidden;
- serve's SDK extensions (e.g. `submission_closed`) are individually
  annotated with their introducing version in this document;
- The persisted form of `RolloutRecord` is in
  `crates/protocol/zhuye-protocol/src/recorder.rs`:
  `SessionMeta` (first record) / `Message` / `Compaction`
  (resume replays compaction boundaries) / `Fork` (fork marker) /
  `Checkpoint` / `DiscussionTranscript` / `TokenCount` (token /
  cost index). Files rotate at 256 KiB × 3, single records are
  truncated at 16 KiB + secrets redacted (see
  [docs/sanitize.md](../docs/sanitize.md));
  `truncate_after` supports physical truncation for rewind (writes a
  `.bak` first).
- `tool_execution` records carry `session_id`, `turn_id`, `call_id`,
  `tool_name`, `phase`, and optional `is_error`. The separate
  `.tool-journal` ledger survives session rotation and rewind. Older readers
  skip the unknown variant and cannot display this ledger; newer readers reconcile
  it together with session records.
- `history_snapshot` records the turn ID, replayed record count, last message
  turn ID, and visible history message count without message content. The count
  is a replay count, not a stable file offset across rotation. Older readers
  may skip this unknown record; strict third-party decoders must be updated.
- `provenance_snapshot` preserves observed and tainted source keys at compaction or
  before a subagent result is written to history. Tool-result `metadata.provenance` contains
  `source`, `source_key`, and `tainted`. Strict older decoders need updating;
  source labels do not replace permissions or sandbox decisions.
- `dynamic_context_snapshot` stores the optional dynamic todo state for recovery
  after compaction. Older strict decoders need updating for this record.

## 1. Startup and Handshake

```
zhuye serve [--resume <uuid> | -c | -r <N>] [--agent <name>] [--plan-mode] ...
```

After the process is ready, it **proactively** writes one global event
to stdout (at this point stdin has no input yet):

```json
{"id": "", "msg": {"type": "session_configured", "session_id": "<uuid>", "model": "...", "provider": "...", "approval_policy": "auto", "sandbox_policy": "workspace_only"}}
```

The client treats receipt of `session_configured` as handshake
complete (a 30s timeout is recommended). `id == ""` denotes a global
event (not belonging to any submission).

Offline testing: `ZHUYE_MODEL=mock` (optionally
`ZHUYE_MOCK_SCRIPT=<JSONL path>`) starts the built-in mock provider,
no API key, no network.

## 2. Submission input (stdin)

```json
{"id": "<client-uuid>", "op": {"type": "user_input", "items": [{"type": "text", "text": "你好"}]}}
```

- `id` is generated by the client (uuid recommended); all turn events
  produced by this submission come back to stdout with the same
  `id` — this is the correlation key by which the client routes
  events.
- Ops without turn semantics (e.g. `register_tools`) also use the
  Submission envelope; the `id` can be any value (their error
  reports use the global `id=""`).
- **Malformed lines do not terminate the session**: when JSON parsing
  fails, serve emits an `error` event with `id=""`
  (`code: "invalid_submission"`) and continues reading the next
  line.

Common Ops (full definitions in
`crates/protocol/zhuye-protocol/src/op.rs`):

| op.type | Fields | Description |
|---------|--------|-------------|
| `user_input` | `items: [{type:"text", text} | {type:"image", data, mime_type} | {type:"file", path, range?} | {type:"local_image", path} | {type:"skill", name, args?} | {type:"question_answer", request_id, answers}]`, optional `thread_settings` | Submit one turn of conversation. `local_image` reads the file from disk by path and converts it to an inline image; `skill` injects the body; `question_answer` releases a pending `ask_user_question` gate (same semantics as `ask_user_question_response`) and does not enter the conversation content |
| `interrupt` | optional `child_id` | Interrupt the current turn |
| `tool_approval` | `id`, `decision` | Respond to an approval request. `decision` is a `ReviewDecision` (serde snake_case): the string `"approve"` / `"approve_for_session"`, or the object `{"deny":{"reason":"..."}}` |
| `register_tools` | `tools: [{name, description, parameters}]` | **serve-local**, register client-defined custom tools |
| `tool_execution_response` | `call_id`, `output` | **serve-local**, remote tool execution receipt |
| `shutdown` | — | Graceful exit (see §6) |
| `rescan_extensions` | `skills: bool`, `commands: bool` | **new in v1.x (additive)**: rescan the extension directories at runtime (skills are replaced by file-type skills in startup directory order; plugin injection and built-in packages are unaffected); does not open a turn — after answering with `extensions_rescanned`, finishes with `submission_closed`. The `commands` bit currently always returns `false` (command bodies are read from disk in real time) |
| `query_guard_stats` | — | **new in F01 (additive)**: query the prompt_guard verdict statistics (four counters: definition-side block/annotate + output-side block/annotate). Does not open a turn — after answering with `guard_stats`, finishes with `submission_closed`; when the guard is disabled, `enabled=false` and the counters are always 0 |
| `mcp_elicitation_response` | `id`, `action`, optional `content` | **new (additive)**: answer an MCP server's user-interaction request (the `mcp_elicitation` event). `id` pairs with the event's `request_id`; `action ∈ accept/decline/cancel`; `content` holds the form values, keyed by the event's `kind.fields[].name` (server schema property names, not renameable); omit it for the `link` form. Without a reply the engine settles the request as `cancel` after the TTL (default 300s, tunable via `ZHUYE_MCP_ELICITATION_TTL_SECS`) — fail-closed |

`thread_settings` supports `model`, `approval_policy`
(`auto` / `prompt` / `deny` / `auto_approve` /
`full_access`), `sandbox_policy` (`workspace_only` /
`os_sandbox` / `full_access`) and `max_tool_concurrency`. The
`effort` and `permission_mode` fields in older SDK types are not
read by this object and should be submitted via `set_effort` and
`set_permission_mode` respectively.

`register_tools` / `tool_execution_response` are handled in place
by the serve process in the stdin loop and **do not enter** the core
submission loop. Two registration-failure cases are reported via
global `error` events, and the tool is skipped:

- `code: "tool_name_invalid"` — empty tool name;
- `code: "tool_name_conflict"` — name collides with a built-in or
  already-registered tool (no overwrite; the client renames and
  retries).

A successful registration has no receipt event (silently
accepted).

## 3. Event output (stdout)

```json
{"id": "<submission-id>", "msg": {"type": "agent_message_delta", "delta": "你"}}
```

Turn events (carrying the submission `id`) are emitted in temporal
order. A typical turn:

```
turn_started → [thinking_delta | agent_message_delta | agent_message]*
             → [tool_call_begin → tool_call_args_delta* → tool_execution_request? → tool_call_end]*
             → [approval_request?] → turn_complete
```

Core variants the SDK cares about (full list in
`event_msg/mod.rs`):

| msg.type | Key fields | Description |
|----------|-----------|-------------|
| `session_configured` | `session_id`, `model`, `provider` | Handshake complete (global) |
| `turn_started` | `turn_id` | Turn begins |
| `agent_message_delta` | `delta` | Incremental text |
| `agent_message` | `text` | Complete message (non-streaming provider) |
| `tool_call_args_delta` | `call_id`, `delta` | **new in v1.5 (additive)**: raw JSON fragments of the tool arguments being generated by the model; concatenate by `call_id` and arrival order to get the complete arguments. Old clients simply ignore the unknown `type` |
| `tool_call_begin` / `tool_call_end` | `call_id`, `tool_name`, `output`, `is_error` | Built-in tool calls |
| `tool_execution_uncertain` | `session_id`, `turn_id`, `call_id`, `tool_name` | The recovered execution outcome is unknown and may have caused side effects; it is not automatically retried |
| `task_budget_snapshot` | `task_id`, `turn_id`, `estimated_tokens`, `actual_tokens`, `reserved_tokens`, `unknown_estimated_tokens`, `unknown_calls`, `estimate_overrun_tokens`, `dispatched_subagents` | Point-in-time shared task-tree budget snapshot. Idle cache warming emits a global snapshot for the originating task and turn after settlement. Estimates include later-cancelled reservations. Treat snapshots for the same `task_id` as cumulative readings |
| `tool_execution_request` | `call_id`, `tool`, `args` | **remote tool**: request local execution by the client (see §5) |
| `approval_request` | `request_id`, `kind`, `risk` | Waiting for a `tool_approval` receipt |
| `error` | `code`, `message` | Session-level error |
| `turn_complete` | `turn_id`, `status`, `usage` | Terminal state of the turn (`success` / `max_iterations` / `stopped` / `token_budget_exceeded`) |
| `turn_aborted` | `turn_id`, `reason` | Turn was interrupted (terminal) |
| `shutdown_complete` | — | Session shutdown finished (terminal, see §6) |
| `submission_closed` | — | This submission's per-turn channel has been drained (terminal, see below) |
| `extensions_rescanned` | `skills: usize`, `commands: bool` | **new in v1.x (additive)**: the response to `rescan_extensions` — total entry count after rescanning the skills directory; `commands` is currently always `false`. The event is delivered via both the per-turn channel and session fan-out (the client deduplicates by submission id) |
| `guard_stats` | `enabled`, `definitions_blocked`, `definitions_reviewed`, `outputs_blocked`, `outputs_reviewed` | **new in F01 (additive)**: the response to `query_guard_stats` — a snapshot of prompt_guard verdict statistics (session cumulative). Dual-path delivery as above |
| `mcp_elicitation` | `request_id`, `server`, `message`, `kind` | **new (additive)**: an MCP server asks the user for input. `kind.type` is `form` (with `fields[]`: name / title / description / required / input kind) or `link` (with `url`). Global event (`id=""`), answered with `mcp_elicitation_response` |

For a successfully launched foreground `bash`, `tool_call_end.output.metadata.network_restriction`
reports `blocked_sockets` (Linux seccomp), `local_only` (macOS Seatbelt allows
local and Unix sockets), or `unrestricted`. Failed launches return a tool error
instead of claiming installation; other tools need not supply this field.

`ReadMcpResource` preserves text and binary resource contents in server order.
Binary items are JSON text blocks containing `uri`, `blob` (base64), and an
optional `mimeType`. `metadata.content_descriptors` follows the same order and contains
`uri`, `mime_type`, and `kind`; binary items also have `encoding: "base64"`.
Embedded resources and resource links returned by MCP tools are JSON text;
hosts should tolerate unknown fields.

An MCP server's `timeout_ms` also applies to connection initialization and the
initial tool listing. Timeouts are reported in `mcp_server_failed` with
`server`, `error`, and `will_retry` fields. Startup currently does not retry
automatically, so `will_retry` is `false`.

MCP interaction requests (`mcp_elicitation`): an MCP server asks the host for
input while a tool call is in flight. The engine turns it into the global
`mcp_elicitation` event; the host answers with `mcp_elicitation_response`
(`action` and `content` are passed through to the server verbatim). For the
`form` shape, `content` must satisfy the server schema — the keys are exactly
`kind.fields[].name`; the engine never renames fields. Without a reply the
engine settles the request as `cancel` after the TTL (default 300s) and sends
that to the server, so an MCP call never hangs forever.

Parallel tool arguments from OpenAI-compatible streams, Responses and
Anthropic may arrive interleaved. Argument deltas of the first tool
are forwarded in real time; the remaining tools' arguments are
forwarded in call order at the end of that model output, ensuring one
`call_id`'s argument fragments never mix into another tool.

In-stream errors from Anthropic and failed terminal states from
Responses enter the error or failover path; when Responses hit the
output limit, continuation is attempted, and unfinished tool calls are
not executed. When no visible output has been produced yet, a stream
break can be retried automatically or switched to another credential;
once text, thinking or tool-call events have been emitted, a stream
error ends the turn and emits `error`; the text already output is
attempted to be written to the session record before that error
event, and the caller can submit a new turn to continue.

Terminal-state semantics: the turn event stream ends with
`turn_complete` / `turn_aborted`. Note that
`shutdown_complete` **carries the id of the shutdown submission**
(not the global `id=""`); consumers subscribed to that id terminate
on it.

`submission_closed` (new in v1.3, additive, non-breaking) is emitted
by serve after each submission's per-turn channel is drained, and
**carries that submission's id**. It lets the `submit()` iterator of
non-turn operations (`compact` / `rewind` /
`set_permission_mode` / `cycle_permission_mode` / goal / plan,
etc. — these operations have no `turn_complete` terminal event) also
finish deterministically; the client treats `submission_closed` the
same as `turn_complete` / `turn_aborted` as the iterator's end.
Turn submissions are first terminated by `turn_complete` /
`turn_aborted`; when their `submission_closed` arrives, listeners
have already removed it and it is harmlessly dropped.

## 3.1 hooks default behavior (serve-specific)

serve is the SDK embedding entry point; the built-in hooks
(`verification` / `search_budget` / `test_runner` /
`plan_completion` / `langfuse_tracker`) are **not enabled by
default** and only take effect when explicitly listed under
`~/.zhuye/config.toml` `[hooks].enabled`. exec / TUI are unaffected
(unconfigured = all enabled). The reason for this difference: Stop
hooks like `verification` run `cargo test` in the host's cwd and
veto turn completion — slow and unpredictable for embedders.

## 4. Concurrency and Ordering

- Submissions may arrive before the previous turn ends. Turns run concurrently
  by default and may share a workspace; events are routed by submission `id`.
  With `[turn_scheduling] serial = true`, user turns queue in arrival order,
  while approval and question responses remain responsive. Interrupt and
  shutdown send `turn_aborted` for queued inputs.
- All events are written serially to stdout by a single writer task;
  **global ordering is guaranteed**.
- An `interrupt` without `child_id` interrupts all in-flight turns
  and cancels the subagents those turns are waiting on; interrupted
  turns end with `turn_aborted`. When `child_id` is specified, only
  that subagent is cancelled and the parent turn can continue
  processing results.
- A subagent only returns as a successful tool result after it has
  received `turn_complete` and its result has been extracted;
  mid-way errors and incomplete replies are returned to the parent as
  tool failures, and status queries distinguish `failed` from
  `cancelled`.
- Subagent tool calls that need approval forward the
  `approval_request` to the parent submission; `tool_approval` /
  hook approvals wake the corresponding subagent through the
  session-shared waiter.
- `ask_user_input` / `ask_user_question` are likewise forwarded to
  the parent submission; the corresponding response Ops are routed
  back to the subagent via the shared waiter.
- Subagents inherit the parent session's permission resolver,
  permission mode, YOLO classification and sandbox configuration;
  tools explicitly denied at the parent level cannot be routed around
  approval inside a subagent.
- The default result extraction returns only the assistant text after
  the subagent's last tool step; process text before tool calls can be
  observed via `subagent_progress` and is not concatenated into the
  final result.
- When calling `call_<role>`, `context_tail` can pass the tail
  messages of the parent session; the default `0` passes no
  history. If truncation falls on tool results, that batch of calls and
  results is padded forward to keep them paired; in-flight delegation
  calls are not passed to the subagent.
- The `mode` argument of `call_<role>` selects how the subagent is
  dispatched: the default `sync` blocks the parent turn until the
  subagent finishes; `async` returns a placeholder receipt at once
  (`tool_call_end` → `output.metadata` carries `async`, `pending` and
  `child_id`) while the subagent runs in the background. The turn
  suspends once the model has nothing else to do; the result is injected
  as a user `<system-reminder>` and written to the session record, then
  the turn continues within itself (a single `turn_complete` overall).
  An async subagent never outlives the turn that dispatched it —
  interrupting the parent turn cancels its in-flight async subagents too.
- Text already streamed from the model before `turn_aborted` is
  attempted to be written to the session record, so later turns can
  recover it.
- The optional local timeout of the TypeScript `prompt` does not send
  an `interrupt`; a turn the server has already accepted may still
  run, and the caller can explicitly interrupt if needed.

## 5. Remote tool execution flow (custom tools)

```
client                                zhuye serve
   │ ── submission: register_tools ──▶ │ (silently registers RemoteTool)
   │ ◀──── tool_execution_request ──── │ remote request (call_id=r1)
   │ executes handler(args) locally    │ (waits on oneshot, default 120s timeout)
   │ ── submission: ─────────────────▶ │
   │    tool_execution_response        │
   │    {call_id: r1, output}          │
   │ ◀──── tool_call_end (model call id) ─ │ LLM gets the result and continues generating
```

- `tool_execution_request` is delivered as a **global event**
  (`id=""`) — it belongs to the tool call and is not part of any
  submission.
- The `call_id` in the request is the receipt id generated by the
  remote bridge, which is **not** the same id as the call id in the
  model events `tool_call_begin` / `tool_call_end`.
- `output` is a `ToolOutput` wire object:
  `{content: [{type:"text", text}], is_error: bool, metadata: {},
  elapsed_ms: int}`. When the SDK's handler throws, it should be
  converted into a text receipt with `is_error=true` (so the LLM sees
  the error instead of hanging).
- If no receipt is received within the timeout (env
  `ZHUYE_REMOTE_TOOL_TIMEOUT_SECS`, default 120s), the core ends the
  tool call with an error output; the turn continues but the tool
  result is error text.
- If the model's tool arguments are not valid JSON, the server neither
  executes the tool nor calls the host handler; the corresponding
  `tool_call_end` is an error, and after the model receives that tool
  error it can continue.
- Interrupting a turn cancels the server-side wait and cleans up
  receipt matching; a handler the client has already started is not
  force-stopped, its late receipt is ignored, and its side effects are
  managed by the client itself.

## 6. Exit semantics

Graceful path: the client sends `shutdown` → serve triggers core
cancellation and emits `shutdown_complete` (carrying that shutdown
submission's id) → the process exits with 0. If a turn is still
running at shutdown, that turn ends with `turn_aborted`.

- **stdin EOF** is equivalent to shutdown (suited to pipe scenarios:
  closing stdin finishes the session).
- Recommended client close flow: write `shutdown` → close stdin →
  wait for the process to exit with a time limit (~2s) → kill on
  timeout.
- When the process exits abnormally, the client should terminate all
  pending submission consumers with an error.

## 7. Error format

```json
{"id": "", "msg": {"type": "error", "code": "invalid_submission", "message": "...", "details": {"line": "<truncated preview>"}}}
```

Current values of `code`: `invalid_submission` /
`tool_name_invalid` / `tool_name_conflict`; the rest are the core's
existing error codes (see `ErrorEvent`). Error events do not
terminate the session; the client decides whether to retry or close.
